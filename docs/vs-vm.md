# 为什么不用虚拟机（以及和其它远程方案的对比）

先把结论说在前面：

> **如果目标只是"让一个人随时能用上这个桌面应用"，虚拟机付出的成本远大于收益。**
> 虚拟机真正值得用的场景是：需要系统级隔离、多人多租户、需要跑不同内核/驱动、需要快照回滚做实验。

---

## 一、和"虚拟机里跑桌面"的对比

| 维度 | 虚拟机方案 | 本项目（无头 X 会话） |
| --- | --- | --- |
| 常开主机 | 需要一台性能足够的机器，且不能休眠 | 复用本来 7×24 的 NAS |
| 内存 | 整机 4–8 GB 起 | 约 300–800 MB（应用 + X + VNC） |
| 磁盘 | 系统镜像 20 GB+，随快照膨胀 | 只有应用与用户数据，通常 < 2 GB |
| 启动 | 宿主开机 → 虚拟机自启 → 进桌面 → 拉应用 | systemd 直接拉起，秒级 |
| GPU | 部分桌面需要 3D 加速，虚拟化下易黑屏 | 不用 GPU，纯软件渲染（见下方说明） |
| 分辨率 | 固定虚拟显示器，改分辨率要重启 X | `xrandr` 运行期调整，跟随窗口 |
| 剪贴板 | 依赖 Guest Additions / VMware Tools | 自建桥，UTF-8 + 图片 |
| 升级应用 | 进虚拟机操作，或重装镜像 | 换 deb + `systemctl restart` |
| 备份 | 镜像/快照，几十 GB | 打包用户目录，几百 MB |
| 迁移 | 镜像与虚拟化平台绑定 | 脚本 + unit 文件，重放即可 |
| 隔离性 | **强**：整机隔离、可快照回滚 | **中**：与宿主同一用户会话 |
| 图形性能 | 中（有 3D 加速时更好） | 偏弱（文本/网页够用，软件渲染） |
| 维护复杂度 | 高（系统更新、驱动、时间同步） | 低（无系统层） |

### 省的是结构性开销，不是渲染本身

需要先厘清一个容易被误解的点：**Xvfb 里没有 GPU，Chromium / Electron 依然走软件渲染（SwiftShader / llvmpipe）**，这一点和虚拟机里的桌面没有本质区别——本项目并没有用上硬件加速。

两套方案的真正差别，是虚拟机要在软件渲染之上再叠四层固定开销：

1. **vCPU 静态切分**：给 2 核，跑重了就排队；给 4 核，宿主核心又一直被占着。本质是"静态切分"对"动态共享"；
2. **重复的完整操作系统**：第二套内核、第二套 systemd、第二套桌面环境与字体缓存；
3. **镜像 I/O 多一层**：qcow2 / raw 的写放大、virtio 栈，宿主页缓存和 guest 页缓存各存一份；
4. **启动路径长**：开机 → 引导 → 进系统 → 起桌面 → 开应用，每多一环就多一次等待。

本项目与宿主共用同一个内核、同一套页缓存、同一个 CFS 调度器：哪个进程需要 CPU 就给它，空闲立刻归还。所以"没有中间商"的准确含义是**少了这四层虚拟化开销**，而不是"用了硬件加速所以不卡"。

还有一个针对 NAS 的现实理由：**iGPU 通常只有一个**。以飞牛 NAS 为例，影视转码正占着核显；虚拟机一旦做 GPU 直通，宿主转码就得让位，等于二选一。而无头会话根本不用 GPU，不跟其它服务抢——这条比"省 CPU"更戳中这类用户的实际痛点。

### 对弱 CPU（N100 / N5105）的合理预期

说实话：比同配置虚拟机更顺，但**不会从"卡"变成"不卡"**。软件渲染这一档，界面滚动、长列表重绘仍可能掉帧；优势主要体现在"宿主还跑着转码、下载、Docker 等服务时，不会被 vCPU 预算卡死"。

### 成本感受（按家庭场景估算）

- 一台常年开机的迷你主机：待机 8–15 W，一年约 70–130 度电；
- 一块 20 GB 的虚拟机镜像 + 快照：占掉 SSD 一大块，且备份很慢；
- 真正的时间成本在**维护**：系统更新失败、显卡驱动、远程协议掉线，每次都要进虚拟机"修"。

本项目把这些都省掉，代价是**放弃整机隔离**（见下）。

### 什么时候该选虚拟机

- 需要跑不受信任的软件，担心影响宿主；
- 需要给多个人各自一个独立桌面；
- 需要不同发行版/内核做兼容性测试；
- 需要"关机前拍快照，出问题一键回滚"。

这些需求本项目都不满足，也不打算满足。

## 二、和向日葵 / ToDesk / RDP 的对比

| 维度 | 商业远控 | 本项目 |
| --- | --- | --- |
| 被控端 | 必须有一台开着的 Windows/macOS | Linux 无头即可 |
| 授权 | 免费版限速/限设备，商用需付费 | 无订阅 |
| 剪贴板 | 厂商实现，中文/图片时好时坏 | 自建，可控可调 |
| 分辨率 | 跟随被控端 | 跟随客户端窗口 |
| 隐私 | 画面经厂商中继（多数情况） | 直连自己的服务器 |
| 多端 | 每台设备装客户端 | 浏览器零安装 |
| 一致性 | 依赖厂商版本 | 代码即配置 |

商业远控的优势是"开箱即用、穿透能力强"。如果你的网络环境无法做端口映射或反代，它们更省事；本项目需要你至少有一条能到达 NAS 的链路（公网端口、Tailscale、Cloudflare Tunnel 等）。

## 四、资源实测（参考值）

在一台 N100 / 16 GB 的 NAS 上（**空载小会话**口径；会话越大占用越高，见下方注记）：

| 项目 | 占用 |
| --- | --- |
| Xvfb + openbox + tint2 | 60–120 MB |
| 应用本体（空载） | 250–450 MB |
| x11vnc + websockify | 30–60 MB |
| clipbridge | 20 MB |
| 合计 | **约 400–650 MB** |
| 空闲 CPU | < 3% |
| 一路 1080p 画面（局域网） | 2–6 Mbps；公网视变化量而定 |

对比之下，一个装了桌面环境的虚拟机空载通常就要 1.2–2 GB。

> **注记（实测）**：上表是刚启动、小会话时的理想值。Electron 是多进程架构，随着会话历史变长，占用会明显上升——作者实测一个约 450 MB 的长会话，全部进程 RSS 合计约 3.3 GB，主窗口渲染进程单核满载（整机口径 CPU 约 40%+）。好消息是这部分开销和虚拟机一样属于软件渲染的固有成本，不是本项目独有的缺陷；差别仍在于没有 vCPU 静态切分和重复 OS。若追求更高帧率，可考虑进阶方案（见下）。

## 五、进阶：想再快一点，换显示后端而不是挤 CPU

如果界面确实卡顿，继续给 Xvfb 加 CPU 收益有限。一个可选方向是把 Xvfb 换成 **weston 的 headless 后端 + wayvnc**：

```bash
weston --backend=headless-backend.so + wayvnc
```

weston 的 headless 后端支持 GL renderer，能读取 `/dev/dri`，在 Intel UHD 核显上做真正的硬件渲染，解码上限也更高。取舍是：

- **Xvfb**：兼容性最好，工作稳定，纯软件渲染；
- **weston + wayvnc**：性能更好，但会占用 iGPU——假如宿主还要跑影视转码，就和"不跟其它服务抢 GPU"的初衷冲突了，需要自己权衡；同时部分老客户端对 Wayland 链路的兼容性未经验证。

> 这是**未实测的进阶方向**，仅作技术提示；本项目默认、文档与脚本仍以 Xvfb 为准，不声称对该路径提供支持。

## 六、怎么选（决策表）

| 你的情况 | 建议 |
| --- | --- |
| 家里有 NAS，想随时随地在任何设备上接着用 | **本项目** |
| 只有一台常开的 Windows，不想折腾 | 商业远控 |
| 需要给家人/同事各自独立桌面 | 虚拟机 / 多用户方案 |
| 需要跑不可信程序 | 虚拟机 + 快照 |
| 内网只有 IPv6 或无法映射端口 | 本项目 + Tailscale/Cloudflare Tunnel |
| 对画质/帧率有要求（视频剪辑、3D） | 本地机器，不要远程 |

## 七、一句话总结

虚拟机买的是**隔离**，本项目买的是**可达性与一致性**。
对"一个人、一个应用、随时接着用"这个目标，后者的性价比高一个数量级。
